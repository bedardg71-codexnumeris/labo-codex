Étapes de travail
Étape 1 — Vérification architecturale automatisée
	∙	Lancer le skill verifier-architecture (SSOT)
	∙	Lancer le skill verifier-noms-stables (registre protégé)
	∙	Vérifier le namespacing : rechercher les accès directs à localStorage/IndexedDB sans cle()
Étape 2 — Audit approfondi : Module Travaux
Pour chaque axe :
	∙	Architecture : communication inter-modules, respect SSOT, couplage avec évaluation
	∙	Code mort : fonctions non appelées, variables inutilisées, CSS .travaux-* orphelin
	∙	Robustesse : try/catch autour des accès IndexedDB/blob, promesses non gérées, race conditions (identifiées en SESSION.md)
	∙	Performance : listeners non nettoyés (canvas), reflows dans les boucles, taille des blobs stockés
Étape 3 — Audit approfondi : Module Évaluation
	∙	Architecture : cascade de priorité modeNote, source unique pour les pratiques actives
	∙	Code mort : anciens sélecteurs/fonctions pré-refonte
	∙	Robustesse : intégrité des données (bug #71 perte inter-cours comme symptôme), verrouillage
	∙	Performance : sérialisation/désérialisation des évaluations, filtrage par groupe
Étape 4 — Audit approfondi : Module Trimestre
	∙	Architecture : namespacing systématique, CLES_NAMESPACEES complètes, pattern bibliothèque+assemblage
	∙	Code mort : fonctions v1 encore présentes, migration incomplete A2025
	∙	Robustesse : gestion multi-cours, fallbacks, données orphelines
	∙	Performance : synchro localStorage↔IndexedDB, taille des structures
Étape 5 — Audit approfondi : Module Planification
	∙	Architecture : gestion d’état (Map vs objets), persistance carte
	∙	Code mort : code pré-refonte toolbar/footer
	∙	Robustesse : gardes anti-cycle (#125), gestion DOM avec display:none
	∙	Performance : rendu SVG, re-layout des conteneurs, événements souris
Étape 6 — Audit approfondi : Modules Suivi des apprentissages
Les modules les plus anciens du projet, avec des enjeux spécifiques :
	∙	Architecture : duplication connue des calculs d’indices A-C-P entre portfolio.js, tableau-bord-apercu.js, profil-etudiant.js et graphiques-progression.js. Vérifier si les clés de stockage (presences, indicesCP, indicesAssiduiteDetailles, portfoliosEleves) passent bien par cle() (namespacing). Évaluer la faisabilité d’un module centralisé indices.js.
	∙	Code mort : fonctions héritées des versions antérieures, calculs redondants, code de migration non nettoyé. portfolio.js était prévu pour être renommé indices-cp.js — vérifier si les deux coexistent.
	∙	Robustesse : profil-etudiant.js (8 866 lignes) est le plus gros fichier de suivi — vérifier la gestion des cas limites (étudiant sans présences, sans évaluations, changement de groupe en cours de trimestre). Vérifier la cohérence des indices quand les données sources changent (ajout/suppression de présences, modification d’évaluations).
	∙	Performance : graphiques-progression.js crée des graphiques Chart.js — vérifier la destruction des instances (chart.destroy()) pour éviter les fuites mémoire. tableau-bord-apercu.js recalcule les métriques globales — vérifier si le recalcul est déclenché trop souvent (à chaque navigation ?). profil-etudiant.js charge potentiellement beaucoup de données — vérifier le lazy loading.
Étape 7 — Survol des autres modules
	∙	Passe rapide sur chaque module restant : repérer les patterns problématiques récurrents
	∙	Vérifier la cohérence des conventions (nommage, structure, commentaires)
