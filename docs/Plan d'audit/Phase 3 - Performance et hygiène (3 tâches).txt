 Tâche 1 — Throttle drag planification via requestAnimationFrame

 Fichier : js/planification-carte.js
 Ref audit : PLN-03

 Problème : 8 handlers mousemove dans la carte mentale fonctionnent sans throttle. Le
  pire cas est onMoveGroupe (ligne 2631) : pour N nœuds sélectionnés, chaque frame
 recalcule N positions + N × mettreAJourLiens() (itère TOUS les liens et reconstruit
 le SVG complet par lien). Avec 50 nœuds sélectionnés → N² recalculs par frame à
 60fps.

 Handlers concernés (par priorité) :
 1. onMoveGroupe (ligne 2631) — critique, N nœuds × M liens × reconstruction
 SVG/frame
 2. onMoveA (ligne 2710) — descendance complète + trouverConteneurPour() (itère TOUT)
 3. onMoveB (ligne 2783) — nœud seul + layout thrashing (offsetWidth/Height)
 4. onMoveC (ligne 2870) — conteneur + descendants + trouverConteneurPour()
 5. onMoveD (ligne 2940) — feuille seule + trouverConteneurPour()
 6. Lasso onMove (ligne 4364) — itère TOUS nœuds + forced layout reads/frame

 Handlers mineurs (coût trivial, non traités) : demarrerLien (1474), reancrerLien
 (1654), palettes (4128, 4200, 4260).

 Changement : Ajouter un wrapper rAF réutilisable en haut du module, puis envelopper
 chaque handler critique :

 // Helper rAF throttle (en haut du module, dans le scope IIFE)
 function throttleRAF(fn) {
     let rafId = null;
     return function(e) {
         if (rafId) return;
         rafId = requestAnimationFrame(() => {
             fn(e);
             rafId = null;
         });
     };
 }

 Pour chaque handler, remplacer l'enregistrement :
 // Avant :
 document.addEventListener('mousemove', onMoveGroupe);

 // Après :
 var onMoveGroupeThrottled = throttleRAF(onMoveGroupe);
 document.addEventListener('mousemove', onMoveGroupeThrottled);

 Et dans le removeEventListener correspondant (onUpGroupe), utiliser la même
 référence :
 document.removeEventListener('mousemove', onMoveGroupeThrottled);

 Handlers à throttler (6 paires addEventListener/removeEventListener) :
 1. onMoveGroupe → onUpGroupe (lignes 2658/2653)
 2. onMoveA → onUpA (lignes 2766/2756)
 3. onMoveB → onUpB (lignes 2854/2844)
 4. onMoveC → onUpC (lignes 2931/2921)
 5. onMoveD → onUpD (lignes 2982/2972)
 6. Lasso onMove → onUp (lignes 4432/4418)

 Risque : Faible — les handlers gardent exactement la même logique. Le throttle
 ajoute au maximum 1 frame de latence (~16ms), invisible pour l'utilisateur. Le
 removeEventListener doit utiliser la même ref throttled sinon le listener fuit —
 vérifier chaque paire.

 obtenirDonneesSelonMode('indicesCP') à chaque fois → 150 appels de plus. Total :
 ~300 db.getSync() + JSON.parse pour des données identiques.

 Changement :

 pré-chargées :
 // Avant (ligne 1086) :
 function calculerIndicesEtudiant(da) {
     const indicesA = obtenirDonneesSelonMode('indicesAssiduite') || {};
     const indicesCPEtudiant = typeof obtenirIndicesCP === 'function'
         ? obtenirIndicesCP(da)
         : null;

 // Après :
 function calculerIndicesEtudiant(da, _cacheIndicesA, _cacheIndicesCP) {
     const indicesA = _cacheIndicesA || obtenirDonneesSelonMode('indicesAssiduite')
 || {};
     const indicesCPAll = _cacheIndicesCP || obtenirDonneesSelonMode('indicesCP') ||
 {};
     // Extraire les données de l'étudiant directement depuis le cache
     const indicesCPEtudiant = indicesCPAll[da]?.actuel || null;

 2. Dans la boucle d'appel (ligne 812), pré-charger une fois :
 // Avant :
 const etudiantsAvecIndices = etudiantsActifs.map(etudiant => {
     const indices = calculerIndicesEtudiant(etudiant.da);

 // Après :
 const _cacheIndicesA = obtenirDonneesSelonMode('indicesAssiduite') || {};
 const _cacheIndicesCP = obtenirDonneesSelonMode('indicesCP') || {};
 const etudiantsAvecIndices = etudiantsActifs.map(etudiant => {
     const indices = calculerIndicesEtudiant(etudiant.da, _cacheIndicesA,
 _cacheIndicesCP);

 Impact : L'appel interne à obtenirIndicesCP(da) (portfolio.js) n'est plus utilisé

 Attention : La logique obtenirIndicesCP(da) dans portfolio.js fait plus que juste

 - obtenirIndicesCP(da) → indicesCP[da]?.actuel (portfolio.js:761)

 Tâche 4 — Consolider styles inline dans index.html (phase ultérieure)

 Fichier : index.html
 Ref audit : CSS-01

 Problème : 1 119 attributs style="..." dans le HTML. Les patterns les plus fréquents
  : display: flex (200+), font-weight (300+), font-size: Xrem (200+), gap: Xpx
 (150+). 30-40% sont factorisables via les utilitaires existants dans styles.css
 (lignes 603-684).

 Classes utilitaires existantes (styles.css) :
 - .u-hide → display: none
 - .u-flex → display: flex
 - .u-flex-between → display: flex; justify-content: space-between; align-items:
 center
 - .u-flex-center → display: flex; align-items: center
 - .u-flex-gap-5/8/10/12/15/20 → display: flex; gap: Xpx
 - .u-flex-wrap → flex-wrap: wrap
 - .u-texte-gras → font-weight: 600
 - .u-texte-bold → font-weight: bold
 - .u-texte-medium → font-weight: 500
 - .u-texte-normal → font-weight: 400
 - .u-texte-petit → font-size: 0.85rem
 - .u-texte-mini → font-size: 0.7rem
 - .u-ml-6/10, .u-mr-10 → marges

 Approche : Chantier en plusieurs passes mécaniques (rechercher-remplacer par
 pattern) :
 1. style="display: flex; gap: 10px" → class="u-flex-gap-10" (et variantes gap)
 2. style="display: flex; justify-content: space-between; align-items: center" →
 class="u-flex-between"
 3. style="display: flex; align-items: center" → class="u-flex-center"
 4. style="display: flex" (seul) → class="u-flex"
 5. style="font-weight: bold" / 600 → class="u-texte-gras"
 6. style="font-weight: 500" → class="u-texte-medium"
 7. style="font-size: 0.85rem" → class="u-texte-petit"
 8. Créer de nouvelles classes utilitaires si nécessaire pour les patterns fréquents
 manquants (ex: font-size: 0.9rem, text-align: center)

 Objectif : 1 119 → ~300 inline styles (les restants seront des styles dynamiques ou
 combinaisons uniques).

 Statut : Planifié pour une phase ultérieure dédiée. Ce chantier est mécanique mais
 volumineux (800+ remplacements dans le HTML).
