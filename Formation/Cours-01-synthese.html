1. Une application, c'est du texte

Labo Codex n'est pas une machine figée. C'est un gros paquet de fichiers texte, des instructions que Safari lit et exécute. Trois langages :

  • HTML – le squelette : « ici un titre, là un bouton ».
  • CSS – l'habillage : « le titre est bleu, le bouton arrondi ».
  • JavaScript – le comportement : « quand on clique, calcule la note ».
Analogie
Un gros cartable de plans de cours. Chaque fichier est une feuille, le cartable est l'app. Développer, c'est écrire et réécrire ces feuilles, des milliers de fois.

« HTML5 / CSS3 / JS ES6+ pur »

Les numéros sont des versions, des éditions successives des langages. « ES6+ » désigne les tournures modernes de JavaScript. Le mot qui compte est « pur » (vanilla) : on utilise les trois langages seuls, sans boîte à outils extérieure. La norme du métier serait d'ajouter un cadriciel (React, Vue). Labo Codex y renonce par choix, avec une seule exception, Chart.js pour les graphiques.

Analogie
Cuisiner à partir d'ingrédients bruts plutôt que d'assembler des préparations toutes faites. C'est plus de travail, mais tu sais exactement ce qu'il y a dedans.

Ce que ce choix achète : la pérennité (rien qui puisse être abandonné par son éditeur et casser l'app), la sécurité (moins de code étranger près des données de tes élèves), le contrôle total.

2. Le vrai problème : ça change tout le temps

Une app vit : on corrige, on ajoute. Chaque modification touche du texte qui marchait déjà. De là trois angoisses – et tout l'outillage du métier existe pour y répondre :

  1. « Je viens de casser ce qui marchait. »
  2. « C'était quoi, la version d'avant ? » – écrasée en sauvegardant par-dessus.
  3. « Qui a changé ça, quand, pourquoi ? »

Le réflexe naïf, c'est projet_v2_FINAL_corrigé_vraiment. Ça tient pour un document ; c'est ingérable à l'échelle d'une app.

Git, c'est exactement cette idée des copies, mais faite proprement, automatiquement, avec une mémoire parfaite.

3. Git : un commit est une photo

Un commit est une photo instantanée de l'état complet du projet, rangée avec quatre choses : un message (le pourquoi), la date et l'auteur, un identifiant unique (par exemple a3f9c2e), et un lien vers la photo précédente.

Ce dernier point fait tout : les commits forment une chaîne. Cette chaîne est l'historique, complet et permanent. Les angoisses 2 et 3 sont désamorcées.

Analogie
À chaque étape de correction d'une copie, un photographe photographie la copie entière et l'agrafe à une pile, avec un Post-it expliquant pourquoi. On peut feuilleter la pile et revoir n'importe quel état passé.

Trois précisions

  • Incrémental ? Non au niveau du modèle : chaque commit est une photo complète, et c'est ce qui rend le retour en arrière fiable. Oui en coulisses : Git ne re-range pas les feuilles inchangées et compresse. Garde le modèle mental de la photo complète.
  • Le commit en deux temps : on choisit d'abord ce qui entre dans la photo (add), puis on déclenche (commit). Comme placer les élèves dans le cadre avant d'appuyer.
  • Git est un logiciel, pas une IA : un programme installé sur une machine, piloté surtout en ligne de commande. Créé en 2005 par Linus Torvalds, le créateur de Linux. Gratuit, libre, standard mondial.

4. Les branches : l'idée qui fait tout cliquer

Pendant que je travaille, le code est à moitié fait, donc cassé par moments. Où travailler sans toucher à l'app en service ? Sur une branche.

Le mot est une métaphore : embranchement, sortie d'autoroute, arbre. L'histoire du projet est une route qui se divise à partir d'un point commun. Ma branche avance – photos 4, 5, 6 – pendant que main reste immobile et intact. L'angoisse n°1 est désamorcée : je peux tout casser sur ma branche, l'app officielle n'est pas affectée.

  • Créer une branche ne copie rien : c'est instantané et gratuit.
  • main est le tronc, la ligne officielle – par convention, pas par une règle de Git. Les branches poussent du tronc, avancent en parallèle, puis s'y greffent : c'est le merge. Cycle complet : naître, pousser, se greffer, être coupée (zéro-dette).
  • HEAD est le panneau « tu es ici » : la branche active.
Analogie
main est le plan de cours officiel. Une branche est la version de travail que tu remanies à part, et qui ne devient officielle qu'une fois prête et relue.
Le conflit
Si deux versions modifient la même ligne, Git ne tranche pas tout seul : il demande un arbitrage humain. C'est une des rares fois où il refuse de décider.

5. GitHub : Git mis en commun, en ligne

GitGitHub
Un logiciel, sur une machine, qui fonctionne même hors-ligne.Un site web qui héberge une copie en ligne du projet, pour partager et sauvegarder.
Comme le traitement de texte.Comme le Google Drive.

Il y a donc deux copies : la mienne, locale, et celle en ligne, surnommée origin. Ainsi origin/main se lit « le tronc main tel qu'il est sur GitHub ». Presque tout le travail consiste à garder les deux copies synchronisées.

Pourquoi GitHub est gratuit

Modèle freemium : les entreprises paient et financent les petits usages. L'intérêt de Microsoft, propriétaire depuis 2018 : occuper la position centrale là où vivent les développeurs, ouvrir la porte vers ses services payants, et alimenter son IA Copilot.

Capital
GitHub n'héberge que le code. Les données de tes élèves – trimestres, noms, notes – vivent dans ton navigateur, hors-ligne, et ne vont jamais sur GitHub ni chez Microsoft. C'est tout l'intérêt de l'architecture « hors-ligne, données chez toi ».

6. Les trois verbes : push, fetch, pull

Ce ne sont que des mouvements entre les deux copies.

VerbeEn clairSensModifie mon travail ?
pushj'envoie mes photos en lignemoi → GitHubnon, j'envoie
fetchje vais voir le neuf, sans l'intégrerGitHub → moinon, c'est le prudent
pullje vais voir et j'intègre (fetch + merge)GitHub → moioui

Dans ton cas, ce n'est pas toi qui tapes ces commandes : tu diriges, j'exécute. Et pull sert même sans collègues : le tronc avance entre les sessions, et chaque session neuve doit se resynchroniser sur origin/main avant de travailler.

7. La PR, le robot, la publication

7.1 La PR (pull request)

Après le push, mon travail est sur ma branche, pas dans main. La PR est la demande formelle de greffer ma branche dans le tronc, avec un résumé du pourquoi, une discussion et les vérifications automatiques.

Piège du nom
pull, le verbe, tire vers moi. Une pull request demande à main de tirer mon travail vers lui. Et le push a déjà eu lieu : la PR porte sur le merge, pas sur l'envoi.

À quoi ça sert : ne jamais modifier l'officiel en douce. Un résumé écrit, un sas de tests, une relecture, une porte. Rien ne rentre tant que ce n'est pas vert. La demande va à qui a autorité sur main – les mainteneurs. Chez toi, le relecteur quotidien est surtout le robot de tests : si tout est vert, l'auto-merge greffe la branche automatiquement. S'abonner à une PR, c'est être prévenu de ce qui s'y passe sans aller vérifier.

Analogie
Soumettre un plan de cours à l'approbation avant qu'il n'entre au programme officiel.

7.2 La CI : le robot qui vérifie

CI = Continuous Integration, intégration continue : à chaque intégration, on relance automatiquement toutes les vérifications. C'est exactement ta demande d'origine, « que le développement s'auto-vérifie à chaque ajout ».

Distinction clé
Le robot (GitHub Actions) est un programme, pas une IA. Aucun jugement : il déroule une recette fixe. Moi, je juge, je décide, je peux me tromper. Le robot est bête et constant – c'est précisément ce qui le rend fiable.

Ce qu'il exécute : les recettes rangées dans le projet, sous .github/workflows/. tests.yml installe les outils et WebKit, puis lance Vitest et Playwright ; codeql.yml fait l'analyse de sécurité. Le tout sur une machine neutre, ce qui tue le « ça marche chez moi ». Ces recettes sont des fichiers versionnés comme le reste du code, et c'est nous qui les écrivons, à l'avance.

Rien de tout ça n'a toujours existé. La suite de tests, la « Défense I », a été livrée le 8 mai 2026, née d'un audit qui réclamait une CI bloquante.

Limite honnête
Le robot ne vérifie que ce qu'on lui a appris à vérifier. C'est la faille exacte que le Cours 2 vient combler.

7.3 Le déploiement

main est la version décidée ; il manque la publication. Netlify, l'hébergeur, surveille main et publie automatiquement dès qu'il change : c'est le CD, le déploiement continu. L'imprimeur-distributeur.

  • Production : la vraie app, app.codexnumeris.org.
  • Deploy preview : un brouillon en ligne d'une PR, sur une adresse temporaire, avant la greffe.
Attention
main à jour ne veut pas dire écran à jour. Il faut la publication, et parfois vider le cache du navigateur.

9. Ton parcours personnel

  1. Phase 1 : Sonnet écrivait, tu copiais dans VS Code, « Enregistrer sous… » en renumérotant sur ton disque. Tu étais ton propre Git, à la main – le fameux v2_FINAL.
  2. Phase 2 : GitHub et de vrais commits, poussés avec GitHub Desktop. De vrais commits et de vrais push, mais par boutons : un habillage visuel posé sur Git.
  3. Phase 3, aujourd'hui : je crée le code, je commit, je pousse, je gère branches, PR et CI.
Ce qui n'a pas changé
Dans les trois phases, c'est toujours toi qui décides quoi, et qui juges si c'est bon. Déléguer l'exécution n'est pas perdre la compréhension – c'est même toute la raison d'être de cette formation.

10. Révision

Réponds dans tes mots avant d'ouvrir.

1. Pourquoi « une app, c'est du texte qui change » – et quelles sont les trois angoisses ?
L'app est un paquet de fichiers texte que le navigateur lit ; comme elle vit, chaque modification touche du texte qui marchait. Les trois angoisses : j'ai cassé ce qui marchait ; c'était quoi la version d'avant ; qui a changé ça, quand, pourquoi.
2. Qu'est-ce qu'un commit, et pourquoi une chaîne ?
Une photo complète de l'état du projet, avec message, date, auteur, identifiant, et un lien vers la photo précédente. Ce lien fait la chaîne, donc l'historique complet et permanent.
3. Une branche, c'est quoi vraiment – et pourquoi main ne bouge pas ?
Une voie de travail parallèle née d'un point commun, qui ne coûte rien à créer. Mes commits s'ajoutent sur elle, pas sur le tronc : main reste exactement où il était, donc l'app en service n'est pas touchée.
4. Différence Git / GitHub, et que veut dire origin ?
Git est le logiciel sur la machine, GitHub le site web qui héberge une copie en ligne. origin est le surnom de cette copie en ligne.
5. push, fetch, pull, merge : le sens du mouvement, et l'effet sur mon travail ?
push : moi vers GitHub, sans effet sur mon travail. fetch : GitHub vers moi, sans intégrer. pull : GitHub vers moi et j'intègre, donc mon travail change. merge : réunir deux branches, la greffe au tronc.
6. Pourquoi le robot de la CI est-il plus fiable que moi, et où s'arrête-t-il ?
Il est un programme, pas une IA : il ne juge pas, il déroule une recette fixe sur une machine neutre. Sa limite est la même chose vue de l'autre côté : il ne vérifie que ce qu'on lui a appris à vérifier.
