1. En trois phrases

Cours 1 répond à : qu'est-ce qui se passe, concrètement, entre le moment où je demande quelque chose et le moment où je le vois à l'écran ? Réponse : une app est du texte qui change tout le temps, et tout l'outillage (Git, GitHub, les branches, la CI, Netlify) existe pour que ce changement ne casse rien.

Cours 2 répond à la faille laissée par le Cours 1 : le robot ne vérifie que ce qu'on lui a appris à vérifier – alors comment faire confiance aux tests eux-mêmes ? Réponse : un test ne vaut que s'il est capable de dire non.

Le fil commun : ne jamais confondre l'attestation et la preuve.

2. Cours 1 – la mécanique

2.1 Une app, c'est du texte

Labo Codex est un gros paquet de fichiers texte que Safari lit et exécute. Trois langages : HTML le squelette, CSS l'habillage, JavaScript le comportement. « Pur » (vanilla) veut dire : ces trois-là seuls, sans cadriciel extérieur (seule exception, Chart.js). Ce choix achète la pérennité, la sécurité et le contrôle.

Analogie
Un gros cartable de plans de cours. Chaque fichier est une feuille ; développer, c'est réécrire ces feuilles des milliers de fois.

2.2 Les trois angoisses

Tout l'outillage répond à trois peurs, et c'est la meilleure façon de le retenir :

  1. « Je viens de casser ce qui marchait. » → les branches
  2. « C'était quoi, la version d'avant ? » → les commits
  3. « Qui a changé ça, quand, pourquoi ? » → l'historique

Le réflexe naïf, c'est projet_v2_FINAL_corrigé_vraiment. Git, c'est exactement cette idée de copies, mais faite proprement, automatiquement, avec une mémoire parfaite.

2.3 Le commit est une photo

Un commit est une photo instantanée de l'état complet du projet, rangée avec un message, une date, un auteur, un identifiant (a3f9c2e) et un lien vers la photo précédente. Les commits forment une chaîne : l'historique.

Modèle mental à garder : photo complète (c'est ce qui rend le retour en arrière fiable). En coulisses, Git compresse et ne re-range pas les feuilles inchangées, mais ça ne change rien à ta façon de raisonner.

2.4 La branche, et pourquoi main ne bouge pas

Pendant que je travaille, le code est à moitié fait, donc cassé par moments. Une branche est une voie parallèle qui part d'un point commun : elle avance pendant que main, le tronc officiel, reste immobile et intact. Créer une branche ne copie rien : c'est instantané et gratuit. Cycle : naître, pousser, se greffer (merge), être coupée.

Analogie
main = le plan de cours officiel. Une branche = la version de travail que tu remanies à part, et qui ne devient officielle qu'une fois prête et relue.

2.5 Git n'est pas GitHub

Git est un logiciel installé sur une machine (créé en 2005 par Linus Torvalds, libre, standard mondial – ce n'est pas une IA). GitHub est un site web qui héberge une copie en ligne du projet. Il y a donc deux copies : la mienne, et celle en ligne, surnommée origin. Presque tout le travail consiste à garder les deux synchronisées.

Capital
GitHub n'héberge que le code. Les données de tes élèves vivent dans ton navigateur, hors-ligne, et ne vont jamais sur GitHub ni chez Microsoft.

2.6 Les trois verbes

VerbeEn clairSensModifie mon travail ?
pushj'envoie mes photos en lignemoi → GitHubnon
fetchje vais voir le neuf sans l'intégrerGitHub → moinon
pullje vais voir et j'intègre (fetch + merge)GitHub → moioui

Même sans collègues, pull sert : le tronc avance entre les sessions, et chaque nouvelle session doit se resynchroniser sur origin/main avant de travailler.

2.7 PR, CI, déploiement

  • PR (pull request) : la demande formelle de greffer ma branche dans main, avec le pourquoi écrit. Piège du nom : le push a déjà eu lieu ; la PR porte sur le merge.
  • CI (intégration continue) : à chaque PR, un robot relance toutes les vérifications. Ce robot (GitHub Actions) est un programme, pas une IA : aucun jugement, il déroule une recette fixe. C'est justement pour ça qu'il est fiable. Si tout est vert, l'auto-merge greffe la branche tout seul.
  • Déploiement (CD) : Netlify surveille main et publie automatiquement. main à jour ne veut pas dire écran à jour – il faut la publication, et parfois vider le cache.
toi ─► [besoin] │ moi ─► branche ─► commits ─► push ─► PR ─► CI ─► merge → main
                                                                        │
                                                              déploiement (Netlify)
                                                                        │
                                                                 toi ─► [tu le vois]
Ton parcours
Phase 1 : tu copiais le code dans VS Code et tu renumérotais à la main – tu étais ton propre Git. Phase 2 : GitHub Desktop, de vrais commits mais par boutons. Phase 3 : aujourd'hui. Ce qui n'a jamais changé : c'est toi qui décides quoi, et qui juges si c'est bon.

3. Cours 2 – la preuve

3.1 Un test, c'est un corrigé méfiant

Un test est un deuxième bout de code dont le seul travail est de vérifier que le premier fait ce qu'il doit. Ossature en trois temps, toujours la même : préparer une situation connue (notes 80 et 90), exécuter (la fonction de moyenne), comparer au résultat attendu (85). Différent = rouge. Identique = vert.

Analogie
Une copie dont tu connais la note exacte. Si une modification « recorrige » et trouve 84, le corrigé hurle. Il te dit que ça a changé, pas pourquoi.

3.2 Deux sortes de tests

Unitaire (Vitest)Intégration (Playwright)
Échelleune fonction isoléel'app entière dans un navigateur
Vitessetrès rapidelent
Attrapeune pièce qui calcule maldes pièces correctes mais mal raccordées

Tester un rouage seul, ou remonter la montre entière et vérifier l'heure. Je peux lancer Vitest ; Playwright, non – c'est la CI qui ouvre vraiment l'app dans WebKit, le moteur de Safari.

3.3 Un test vert ne prouve rien par lui-même

Un test vert ne rassure que s'il était capable de devenir rouge.

Un test qui ne peut pas échouer est une alarme au fil débranché : silencieuse, y compris pendant l'incendie. Il peut vérifier autre chose que ce qu'on croit, tester la mauvaise chose, ou ne jamais s'exécuter à cause d'une faute de frappe. Résultat : une fausse confiance, pire que pas de test du tout.

Ton terrain
Un corrigé qui donne 100 % à toutes les copies, même à la blanche, n'évalue rien. Un instrument ne vaut que s'il peut dire non.

3.4 Le break-test

Si un test ne vaut que s'il peut échouer, il faut le voir échouer pour de vrai. Trois gestes : (1) on introduit exprès le bug que le test doit attraper ; (2) on vérifie qu'il rougit – sinon il est inutile et on le répare ; (3) on retire le sabotage, et le vert veut enfin dire quelque chose.

Vécu, 17 juin : avant de se fier à la sentinelle des maquettes, on a retiré le marqueur estMaquette. Le test a rougi comme prévu. C'est ce rouge-là qui a autorisé la confiance dans le vert.

À doser
On ne fait pas de break-test sur chaque test : on le réserve à ceux qui gardent quelque chose d'important – les données, la sécurité, une règle à ne jamais rebriser.

3.5 La vérification adverse (la posture au-dessus)

Le break-test n'est qu'un cas particulier. La posture, c'est de chercher activement à se réfuter plutôt qu'à se confirmer – contre le biais de l'auteur.

ObjetGeste adverse
un testcasser exprès, exiger le rouge
un correctif de donnéeschercher l'enregistrement qu'il a raté
un correctif de sécuritétenter l'attaque
un calculnourrir d'entrées hostiles : vides, extrêmes, absurdes
un diagnosticsupposer que ma première explication est fausse

Vécu, 17 juin : « je n'arrive pas à supprimer mes maquettes ». Au lieu de coder un bouton, on a vérifié – elles étaient déjà supprimables. Le vrai problème était la découvrabilité. Attester le diagnostic aurait ajouté du code inutile.

3.6 Le golden master

Pour ce qui est trop complexe pour écrire « j'attends 85 » à la main. Un jour où l'on est sûr que le calcul est bon, on enregistre le résultat complet : c'est l'étalon. À chaque passage, on recompare au même étalon, et la moindre dérive rougit. Utile surtout après un refactoring censé ne rien changer.

Le piège
Un golden master ne vaut que si l'étalon figé était lui-même correct – sinon on scelle l'erreur. Capturer n'est pas attester : il faut vérifier l'étalon avant de le sceller.
Le renversement à emporter
Devant un test vert, ne pas demander « est-ce que ça marche ? » mais « est-ce que ce test saurait me dire si ça ne marchait pas ? »

4. Quiz de récupération

Réponds dans tes mots avant d'ouvrir. C'est l'effort de récupération qui fixe, pas la relecture.

1. Pourquoi dit-on qu'une app « est du texte qui change » ?
Parce que l'app est un paquet de fichiers texte (HTML, CSS, JS) que le navigateur lit. Comme elle vit – on corrige, on ajoute – chaque modification touche du texte qui marchait déjà. De là les trois angoisses.
2. Les trois angoisses, et l'outil qui répond à chacune ?
« J'ai cassé ce qui marchait » → la branche. « C'était quoi la version d'avant ? » → le commit. « Qui, quand, pourquoi ? » → l'historique (la chaîne des commits).
3. Qu'est-ce qu'un commit, et pourquoi une chaîne ?
Une photo complète de l'état du projet, avec message, date, auteur, identifiant, et un lien vers la photo précédente. Ce lien fait la chaîne : un historique complet et permanent qu'on peut feuilleter.
4. Une branche, c'est quoi – et pourquoi main ne bouge pas pendant ce temps ?
Une voie de travail parallèle née d'un point commun. Mes photos s'ajoutent sur ma branche, pas sur le tronc : main reste exactement là où il était, donc l'app en service n'est pas affectée même si je casse tout.
5. Git ou GitHub – et que veut dire origin ?
Git est le logiciel, sur la machine, qui fonctionne même hors-ligne. GitHub est un site web qui héberge une copie en ligne. origin est le surnom de cette copie en ligne ; origin/main = le tronc tel qu'il est sur GitHub.
6. push, fetch, pull : sens du mouvement, et lequel modifie mon travail ?
push : moi → GitHub. fetch : GitHub → moi, mais sans intégrer (prudent). pull : GitHub → moi et j'intègre (fetch + merge) – c'est le seul des trois qui modifie mon travail.
7. Pourquoi le robot de la CI est-il fiable, alors que je suis, moi, faillible ?
Parce que c'est un programme, pas une IA : il ne juge pas, il déroule une recette fixe, toujours pareil, sur une machine neutre. Sa limite est l'autre face de la même pièce : il ne vérifie que ce qu'on lui a appris à vérifier.
8. L'ossature en trois temps de tout test ?
Préparer une situation connue, exécuter, comparer le résultat obtenu au résultat attendu.
9. Pourquoi un test vert peut-il ne rien prouver ?
Parce qu'il n'était peut-être pas capable de rougir : il vérifie autre chose que ce qu'on croit, teste la mauvaise chose, ou ne s'exécute jamais. C'est une alarme au fil débranché, et elle produit une fausse confiance.
10. Break-test et vérification adverse : même chose ?
Non. Le break-test est un cas particulier – celui qui s'applique à un test. La vérification adverse est la posture générale : chercher à se réfuter plutôt qu'à se confirmer, que l'objet soit un test, un correctif, un calcul ou un diagnostic.
11. Le piège du golden master ?
Si l'étalon qu'on a scellé était lui-même erroné, on a scellé l'erreur : tout dérivera fidèlement par rapport à une référence fausse. Il faut vérifier l'étalon avant de le figer.
